# 🌟 核心工作铁律 (Critical Rules)
在执行任何代码编写、重构或 Debug 任务时，必须严格遵守以下原则，任何违反将导致任务被退回：

1. **杜绝臆断，基于事实**：在编写或修改代码时，绝对不能进行任何形式的假设。所有不确定的地方（包括函数、类、成员变量、异常定义等），都必须直接通过工具查阅我提供的实际项目代码或本地文档。不能凭空捏造。
2. **拒绝偷懒，完整交付**：在绝大多数情况下，必须提供完整的代码片段或文件内容，而不仅仅是修改建议或部分代码。不允许简化处理与代码实际情况不符的逻辑。
3. **保证逻辑完整性**：重构或实现功能时，确保逻辑闭环。例如：若 API 设计了分页，前端服务就必须完整地处理分页逻辑（包含请求参数和响应数据的完整解析），而不是仅提取列表内容；如果涉及到特定的请求 DTO，就必须使用该 DTO，绝对不能用 `Map` 或其他方式临时替代。
4. **多步骤任务确认**：在执行如大规模代码重构这类多步骤任务时，必须逐步进行，并在每一步完成后与我确认，确保方向正确后再继续。
5. **语言与注释规范**：所有的回复沟通、代码中的注释以及严格的文档注释，都必须使用中文。代码中的函数、异常、成员变量等命名保持英文规范，但相关的解释和说明需为中文。

# 🛠️ 技术栈专属规范

## Kotlin Multiplatform (KMP) 开发规范
- **职责划分**：业务逻辑、网络请求、数据模型 (DTO)、本地数据库操作必须尽可能下沉到 `shared` 模块的 `commonMain` 中。
- **跨平台适配**：遇到必须调用特定平台底层能力时，规范使用 `expect` / `actual` 关键字，并提供至少 iOS 的 `actual` 实现。
- **状态管理**：共享层的状态暴露应考虑到 Swift 端的调用友好性（例如使用由 SKIE 优化过的 StateFlow）。

## Apple 原生端 (SwiftUI) 开发规范
- **视图解耦**：坚持声明式 UI 范式，视图层应保持轻量，严禁在 View 结构体中混入复杂的业务计算逻辑。
- **数据绑定**：配合 KMP 的共享 ViewModel 或底层架构，使用现代的状态管理宏（如 `@Observable`）来驱动 UI 更新。

## 数据库与后端逻辑 (PostgreSQL)
- **表结构对齐**：所有与数据持久化相关的 DTO 和实体类，必须与 PostgreSQL 数据库中实际的表结构、字段类型（如 UUID, JSONB 等）严格对齐。
- **SQL 规范**：如果涉及编写原生 SQL 或数据库迁移脚本，必须遵循 PostgreSQL 语法规范及最佳实践。

# 📚 MCP 工具调用规范
1. **Apple 文档**：遇到 SwiftUI 不确定的 API，必须调用 `apple-docs` (或对应的搜索工具) 查阅最新用法。
2. **KMP 架构**：涉及 KMP 官方库版本或用法争议时，调用 `fetch` 工具读取官方网页核实。
3. **数据库联调**：需要确认远端表结构时，调用 `mcp-toolbox-for-databases` 获取真实 Schema。
